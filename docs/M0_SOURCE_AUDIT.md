Объём: дерево файлов, конфигурация Godot, основные сцены, игровые сервисы, локальные сохранения, Web export presets и GitHub Actions.  
Ограничение: аудит выполнен чтением исходников GitHub. Запуск Godot, headless import, Web export и тесты в локальной среде в рамках этого аудита не выполнялись.

## 1. Структура проекта

Подтверждённые ключевые файлы:

- `project.godot` — Godot 4.3, GL Compatibility, основная сцена `scenes/main.tscn`.
- `scenes/main.tscn` — минимальная сцена-контейнер, подключающая `scripts/main.gd`.
- `scripts/main.gd` — главный координатор игры и построение значительной части UI.
- `scripts/world/isometric_district_world.gd` — основной изометрический мир.
- `scripts/world/isometric_grid.gd` — преобразования координат изометрической сетки.
- `scripts/systems/` — отдельные доменные сервисы.
- `scenes/prototype_3d_district.tscn` и связанные 3D-скрипты — отдельный прототип, не основная игровая сцена.
- `export_presets.cfg` — Web и отдельный 3D Prototype Web presets.
- `.github/workflows/godot-validation.yml` — headless import и запуск основной сцены.
- `.github/workflows/deploy-web.yml` — импорт, smoke test, два Web export и публикация Pages.

В дереве проекта не обнаружены отдельные каталоги `tests/`, `addons/`, `assets/`, `supabase/` или `web/`. Это описание текущего дерева, а не запрет на их добавление по мере необходимости.

## 3. Архитектурные наблюдения и риски

### 3.1 Главный скрипт перегружен

`scripts/main.gd` содержит около 2 818 строк и одновременно:
- создаёт и связывает сервисы;
- создаёт UI и всплывающие панели;
- обрабатывает пользовательские действия;
- координирует сохранение и загрузку;
- обновляет отображение мира.

Это не повод для немедленного масштабного рефакторинга. Рекомендация: сначала завершить платформенную интеграцию минимальными адаптерами, затем постепенно выносить UI-контроллеры и координационные сценарии небольшими PR с регрессионной проверкой.

### 3.2 Autoload не используется

В `project.godot` нет секции `[autoload]`. Сервисы создаются и связываются из `main.gd` через `new()` и `add_child()`. Не вводить глобальные singleton-сервисы без отдельной причины: текущая композиция уже является рабочей точкой входа.

### 3.3 Сохранения пока локальные и без миграций

`scripts/systems/save_service.gd`:
- использует `user://rayon_save.json`;
- записывает поле `version`;
- текущая константа `SAVE_VERSION = 1`;
- при несовпадении версии отклоняет сохранение;
- не содержит механизма миграции между версиями.

`main.gd` собирает состояние доменных сервисов в один Dictionary и сохраняет его. Офлайн-время вычисляется по локальной системной временной метке. Следовательно:
- правило `schema_version` из технической документации пока не реализовано буквально (в коде поле называется `version`);
- безопасной цепочки миграций пока нет;
- локальные системные часы можно изменить, поэтому такой офлайн-расчёт нельзя считать защищённым для конкурентной онлайн-экономики.

Перед облачной синхронизацией нужно разработать версионируемый контракт профиля и миграции, не меняя формат текущих сейвов без переходного адаптера.

### 3.4 Экономика пока клиентская

`EconomyService` содержит локальный баланс, списание и начисление денег. Это подходит для текущего одиночного прототипа, но не может быть авторитетным механизмом экономики в Telegram Mini App с облачными профилями. В целевой онлайн-архитектуре сервер должен подтверждать финансовые операции, а клиент — отображать результат сервера.

Не переносить баланс в Supabase простым разрешением клиенту обновлять произвольное поле. Нужны серверные операции/функции, проверка прав, атомарность и защита от повторного выполнения.

## 4. Telegram и Supabase

В дереве файлов, проверенном на момент аудита, не обнаружены очевидные исходники Telegram WebApp bridge, Supabase-клиента, SQL migrations, RLS policies или Edge Functions. Поиск по репозиторию по ключевым строкам Telegram initData и Supabase client также не выявил совпадений.

Вывод: интеграции не подтверждены исходниками. Перед реализацией необходимо добавить отдельный web-bridge и серверную проверку Telegram initData. Нельзя доверять Telegram ID, присланному клиентом без проверки подписи initData на сервере. Service-role key и другие секреты не должны попадать в Godot Web build.

## 5. Сборка и CI

В репозитории уже есть два GitHub Actions workflow:

1. `godot-validation.yml` — Godot 4.3 container, headless editor import, запуск основной сцены, сохранение логов.
2. `deploy-web.yml` — установка Godot 4.3 и Web templates, import, smoke test, экспорт основного Web preset и отдельного 3D prototype preset, публикация Pages.

Наличие workflow-файлов подтверждено. Успешное выполнение текущей сборки этим аудитом не подтверждено: для последнего документационного коммита не обнаружены связанные workflow runs или status checks. Следующий шаг — запустить workflow на отдельном проверочном коммите/через workflow_dispatch и изучить логи, не объявляя экспорт рабочим до получения зелёного результата.

## 6. Приоритетные действия после аудита

1. Запустить существующие Godot validation и Web export workflows, исправить только воспроизводимые ошибки.
2. Зафиксировать проверенную версию Godot и воспроизводимость Web build.
3. Добавить минимальный Telegram WebApp bridge, который передаёт initData в backend и корректно работает вне Telegram в dev-режиме.
4. Создать Supabase migrations для профиля/сохранения и RLS с закрытым доступом по умолчанию.
5. Реализовать серверную проверку initData и защищённые операции загрузки/сохранения профиля.
6. Спроектировать миграцию локального сейва в облачный профиль; не удалять локальное сохранение до успешной синхронизации и проверки восстановления.
7. Добавить автоматические тесты для критичных доменных операций и миграций.

## 7. Итог

Структура существующей игры и ключевые сервисы подтверждены. Основной технический риск перед Telegram-релизом — переход от локального клиентского состояния к проверяемому серверному профилю без потери уже накопленного игрового прогресса. Поэтому следующий этап — сначала подтверждение сборки и CI, затем минимальная вертикальная интеграция Telegram + Supabase. Массовый рефакторинг `main.gd` и переписывание игровых систем не входят в этот этап.

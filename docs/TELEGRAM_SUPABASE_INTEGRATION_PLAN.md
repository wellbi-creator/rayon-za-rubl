# План интеграции Telegram Mini App и Supabase

Дата: 25.11.2026  
Статус: проектный контракт перед реализацией; интеграция ещё не реализована.  
Основание: GDD 1.0, `docs/M0_FOUNDATION.md`, `docs/M0_SOURCE_AUDIT.md` и проверенные исходники `main.gd`, `SaveService`, Web export preset.

## 1. Цель и границы первого вертикального среза

Получить минимальный, безопасный сценарий:

1. Игра запускается в Telegram Mini App и определяет, доступен ли Telegram WebApp API.
2. Клиент передаёт исходную строку `Telegram.WebApp.initData` в серверную функцию — не отдельный Telegram ID и не разобранный клиентом объект пользователя.
3. Сервер проверяет подпись initData по официальному алгоритму Telegram, проверяет `auth_date` и только после успешной проверки получает доверенный Telegram user ID.
4. Клиент получает короткоживущий Supabase session, связанный с проверенным Telegram ID.
5. Клиент может получить и сохранить только собственный профиль через RLS.
6. Если Telegram API недоступен (редактор Godot/локальный браузер), игра остаётся запускаемой в dev-режиме, но не выдаёт фиктивную Telegram-авторизацию и не получает доступ к облачному профилю.

В этот этап не входят: перенос экономики на клиентские RPC, платежи, магазин, мультиплеер, лидерборды, синхронизация нескольких устройств с конфликтующим одновременным редактированием и удаление локального сейва.

## 2. Что подтверждено текущим кодом

- Основная сцена — `scenes/main.tscn`, главный координатор — `scripts/main.gd`.
- Сервисы создаются в `main.gd`; в `project.godot` нет Autoload.
- `main.gd` собирает состояние всех игровых сервисов в Dictionary в `_save_game()` и восстанавливает его в `_load_game()`.
- `SaveService` хранит локальный файл `user://rayon_save.json`, поле версии называется `version`, текущая версия — 1.
- Локальный сейв включает игровой баланс и все ключевые подсистемы; это ценные пользовательские данные, их нельзя перезаписывать пустым облачным профилем.
- Web export preset называется `Web`; отдельный preset `3D Prototype Web` не является основной игрой.
- В проверенном дереве пока нет Telegram bridge, Supabase client, SQL migrations или Edge Functions.

## 3. Архитектура клиента

Добавить отдельный небольшой адаптер платформы, не превращая `main.gd` в HTTP/Telegram-клиент:

- `web/telegram_bridge.js` — тонкий JS-слой для чтения Telegram WebApp API и передачи данных в Godot.
- `scripts/platform/telegram_platform.gd` — Godot-адаптер с сигналами/методами: Telegram доступен, initData получен, viewport/safe-area сведения получены. Вне Web экспортируемой платформы возвращает состояние «недоступно», а не поддельного пользователя.
- `scripts/platform/cloud_profile_client.gd` — HTTP-клиент только для вызова публичных Edge Functions и операций профиля. Не содержит секретов.
- Один координатор запуска вызывает адаптеры после готовности сцены; не вводить Autoload только ради Telegram.

Предпочтительный путь передачи initData — отдельный JS bridge, вызываемый из Godot Web. Нельзя строить JS-код конкатенацией пользовательских значений. Передача данных должна быть корректно экранирована/сериализована; initData не писать в логи и не сохранять в localStorage или сейв.

## 4. Контракт авторизации

### Запрос клиента

Клиент отправляет исходную строку initData по HTTPS в Edge Function `telegram-auth`. Не отправлять `initDataUnsafe` как доказательство личности.

### Проверка на сервере

Edge Function должна:

1. Проверить наличие обязательных параметров и корректность формата.
2. Извлечь `hash`, построить data-check-string из остальных полей согласно Telegram Mini Apps документации.
3. Вычислить HMAC-SHA-256 с секретным ключом, производным от bot token и константы `WebAppData`, и сравнить хэши в constant-time реализации.
4. Проверить `auth_date` на разумный возраст (конфигурируемый предел, начальная рекомендация — не более 24 часов) и отклонить дату из будущего с небольшим допуском на рассинхронизацию часов.
5. Извлечь Telegram user ID только из подписанного поля `user`.
6. Не возвращать bot token, исходные секреты или избыточные персональные данные в клиент.

Bot token хранится только в Supabase Edge Function Secrets. Он никогда не помещается в Godot, JavaScript bridge, GitHub Pages, GitHub Actions artifacts или репозиторий.

### Supabase session

После проверки сервер выдаёт клиенту ограниченную сессию Supabase, чьи claims/subject однозначно сопоставлены с проверенным Telegram user ID. Предпочтительно использовать Supabase Auth custom access token / поддерживаемый серверный механизм выдачи сессии; конкретный формат токена фиксируется при реализации на актуальной версии Supabase и проверяется тестами. Нельзя просто вернуть клиенту service-role key или использовать service-role key как пользовательский bearer token.

## 5. Минимальная схема облачного профиля

Предлагаемая первая таблица `player_profiles`:

- `telegram_user_id` — bigint/числовой идентификатор Telegram, первичный ключ или уникальный ключ.
- `save_schema_version` — версия сериализованной игровой схемы.
- `save_data` — JSONB с игровым Dictionary.
- `created_at`, `updated_at` — серверные временные метки.
- `revision` — целочисленная ревизия для защиты от случайной перезаписи более новой версии.

Таблица создаётся SQL migration. RLS включается сразу; политики разрешают authenticated-пользователю читать/обновлять только строку, где Telegram ID из проверенного JWT claim совпадает с `telegram_user_id`. Клиент не может сам менять Telegram ID, revision, системные даты или чужие строки. Секреты и сервисные ключи отсутствуют в клиентской схеме.

Не добавлять произвольный открытый INSERT/UPDATE policy на основе присланного клиентом `telegram_user_id`.

## 6. Сохранения и безопасная первая синхронизация

Первая синхронизация должна быть миграцией с явным выбором источника, а не безусловным «облако поверх локального»:

1. Считать локальный сейв через существующий `SaveService`, не менять формат `version = 1`.
2. Получить облачный профиль после авторизации.
3. Если облачного профиля нет, отправить локальный сейв как первоначальный профиль.
4. Если локального сейва нет, а облачный есть, загрузить облачный профиль.
5. Если оба есть и различаются, не перезаписывать автоматически: сохранить обе версии, показать экран выбора/восстановления и записать решение.
6. После подтверждённой загрузки/записи и проверки целостности сохранить локальную копию.
7. Сетевой сбой не должен блокировать запуск одиночной локальной игры и не должен приводить к удалению локального файла.

Время для офлайн-экономики и критичных начислений в будущем должно подтверждаться сервером. На первом этапе нельзя считать клиентские локальные часы достоверными для онлайн-наград или денежных операций.

## 7. Порядок реализации

### T1 — Telegram bridge (без облачной авторизации)

- Подключить Telegram WebApp SDK только в основном Web preset.
- Добавить JS bridge и GDScript adapter.
- Получать initData только в памяти, передавать его через HTTPS в следующий этап.
- Поддержать безопасный режим запуска вне Telegram.
- Проверить Web export и запуск с Telegram WebView; отдельный 3D preset не менять.

### T2 — серверная проверка initData

- Добавить Supabase Edge Function `telegram-auth`.
- Добавить bot token только как серверный secret.
- Реализовать проверку подписи, возраста initData и негативные тесты.
- Не выдавать сессию для неверной подписи, отсутствующего user или просроченного auth_date.

### T3 — профиль и RLS

- Добавить SQL migration для `player_profiles`.
- Включить RLS и тесты изоляции между двумя Telegram-пользователями.
- Настроить безопасную выдачу Supabase user session после серверной проверки Telegram.

### T4 — клиентская загрузка/сохранение и миграция

- Добавить облачный профильный клиент и ревизии.
- Реализовать начальную синхронизацию с сохранением обеих копий при конфликте.
- Проверить сценарии: новый аккаунт, локальный сейв, только облачный сейв, обе версии, сетевой сбой, повторный запрос.
- Не удалять и не инвалидировать локальный сейв до успешного восстановления.

## 8. Критерии готовности

- Неверная/поддельная/просроченная initData отклоняется сервером.
- В репозитории и Web artifacts отсутствуют bot token и service-role key.
- Два пользователя не могут читать/изменять профили друг друга.
- Повторный запрос авторизации безопасен и не создаёт дублирующих профилей.
- Локальная игра работает без Telegram и без сети в явно обозначенном dev/offline режиме.
- Существующий `user://rayon_save.json` сохраняется; миграция не теряет баланс, жителей, здания, бизнес, дороги и прогресс.
- Web Export и headless validation проходят в CI.
- Сквозной сценарий запускается в реальном Telegram Mini App на iOS/Android и в браузере на ПК.

## 9. Внешние зависимости, необходимые при реализации

- Telegram bot token (только для настройки Supabase Edge Function Secret; не присылать в чат и не коммитить).
- Supabase project URL и anon/publishable key (публичные клиентские значения, но должны соответствовать проекту).
- Доступ к Supabase проекту для применения migrations, настройки Edge Functions и secrets.
- Telegram bot с настроенным Mini App URL для end-to-end теста.

До появления этих подключений можно реализовать и проверить локальный bridge и серверные исходники, но нельзя честно объявить production Telegram auth или облачные сохранения готовыми.
